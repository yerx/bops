# Portfolio task router

Choose a process; this skill does not grant execution, scheduling, publication or clinical authority.

1. Read the request and applicable repository instructions, including overrides and existing tighter task/retry limits. Read the relevant [portable policy](references/policy.md) before substantial routing. Establish intent, project, affected stack/paths, evidence, accepted scope, risk, available installed skills/tools, environment and existing authorization. Inspect only necessary context; do not read credentials. Ask only for missing information that changes dependent work; continue authorized independent work.
2. Read [routes](references/routes.md) for the matching intent. Mixed tasks use the primary outcome plus necessary risk branches, not the union of every skill. For small clear work answer or act directly within authorization.
3. Consult the [adoption catalog](references/policy.md#selective-adoption-catalog) selectively. Named practices are not proof of installed skills. If available, read the actual relevant skill before use; disclose missing skills and use the equivalent method without claiming invocation. Preserve source identity: Matt TDD/teach/code-review differ from pstack namesakes; deslop is cursor-team-kit.
4. Give a compact route: intent and evidence; scope/authorization; selected practices and why; concrete output; owner/reviewer/verifier; acceptance commands and environment; stop conditions and next human gate. Collapse this to a paragraph for small work. Never invent repo commands: discover existing commands and distinguish proposed from executed.
5. Execute only if the user's task authorizes execution. Planning selects a route without launching agents or changing apps. A coordinator assigns scope; one builder owns each checkout; review is read-only; a verifier runs actual acceptance without patching source. Extra agents require authorization/capacity, not this router alone.
6. Meaningful changed behavior needs executable checks at exact head or dirty snapshot including relevant untracked hashes. Linux-compatible web/portable tests can use a proven Cloud environment; Xcode simulator/archive checks require macOS and device checks require devices. NOT RUN/BLOCKED is honest when unavailable. Review receipts is INSPECTED_RECEIPTS_ONLY, not RERAN_CHECKS.
7. Return grouped acceptance findings to the original builder within scope; fixes invalidate affected prior checks/verdicts, require reruns and re-review. Stop at the tighter repository/task limit or after two failed repair attempts, contradictory oracle/setup changes, exhausted agreed limits, user stop, missing dependent authorization or tool blockers. Record diagnosis rather than weakening acceptance.
8. Close with actual evidence, unresolved limits and next gate. Merge/release/deployment and clinical actions retain human approval. Never claim a productivity multiplier from anecdotes.

Use existing journals for consequential decision/evidence pointers. Unknown runtime/spend stays UNKNOWN. Unrelated findings enter the observation queue; they do not expand repair authority. See [scenario prompts](references/evaluation-cases.md) for review exercises; they are simulations, not app work.

Bundle identity and source pins: [provenance](references/provenance.json). Use the target project's established journals/queues only within authorization; no canonical machine paths are required.
